Every code change a self-modifying agent proposes, decided by an SMT solver before it lands. One modification at a time, and that turns out to be exactly the problem.

Two decomposition attacks against PAAC are open. Each step individually accepted by the real verifier; the composition violates a safety axiom. Synthesised by Z3, confirmed end to end, published without a defence.

What it is

A solver sits between the agent and its own source

PAAC is a deterministic wrapper. It intercepts a proposed modification, compiles it to a restricted language called SIL, encodes it into a single Z3 query, and admits it only when the solver proves no input inside the declared bounds can drive the program into a state violating a safety axiom. A refusal comes back with a concrete counterexample, not a score.

  1. Intercept. Every modification path routes through one entry point. That entry point is the trust boundary.
  2. Compile. SIL has bounded loops, no recursion, no heap, no concurrency. That restriction is why the decision is cheap, and it is also why SIL cannot express most real code.
  3. Encode. Single static assignment, loop unrolling to the declared bound, and the negation of each applicable axiom added to a violation disjunction.
  4. Decide. UNSAT accepts. SAT rejects and returns the model as a counterexample. Unknown or timeout is an error, never an acceptance.
  5. Attest. An accepted result is signed with Ed25519 over a canonical payload, so a third party can check that verification happened.
The result

We pointed Z3 at our own acceptance condition

PAAC decides one modification at a time and then writes it into the live registry. Nothing re-examines the accumulated program. So we asked a solver for a program and a modification, each individually accepted, whose composition is not safe. Two of three declared schemas produced one. The adversary is Z3 rather than an LLM or random search, so anyone can replay the query.

A. The call site never discharges the contract

decrement is proven safe only for counter >= 1. reset_counter calls it with 0. Both accepted; at runtime the callee computes -1. A call is encoded as an uninterpreted function over its arguments, so a precondition is an assumption inside the callee and an obligation on nobody.

Submitting the caller together with the callee does not help. The compiler rejects a call to an undefined function, so the callee is already in front of the verifier, and the composition is still accepted.

C. A blameless change invalidates an old proof

decrement subtracts 1 and admits counter >= 1. A caller is accepted against it. Then decrement is replaced by a version that subtracts 2 and admits counter >= 2, safe on its own terms. The caller still passes 1.

This is the deeper of the two. Schema A never had a covering proof at the call site; schema C had one and lost it. So enforcing call-site obligations at submission time would not close it. Replacing a function has to re-verify its callers.

What these results do not establish

  • Two witnesses is not a measured attack surface. The denominator is three hand-written schemas. It is not an estimate of how many decomposition attacks exist against PAAC.
  • The boundaries are narrow. Two functions, one call site, a literal argument, one arithmetic operation each, no loops, no branches, holes in [-8, 8].
  • One axiom. Both violate counter_in_range. Decomposition against the other four has not been attempted.
  • A null result would have been bounded too. UNSAT would mean "no decomposition in this schema for these holes", never "PAAC is decomposition resistant".
  • One platform. Windows, Python 3.11.9.

Reproduce both, no seed and no sampling:

# prints every schema next to its boundary, and the summary with its denominator
PYTHONPATH=. python scripts/run_decomposition.py

# the two strict xfail tests that pin the vulnerabilities
PYTHONPATH=. python -m pytest tests/test_decomposition.py -q

The two expected failures are load-bearing

They are strict xfail pins on the two decomposition witnesses. Being strict, they turn into outright failures the moment a composition defence lands, which forces whoever builds it to come back and confirm the attacks are actually rejected. They must not be deleted to make a suite green.

The 200 ms floor is not the cost

Verification responses are padded to a 200 ms floor to remove the timing channel. The real end-to-end cost of one interception on this platform is 2.0 to 2.4 seconds, dominated by process isolation rather than by the solver. Size a deployment against the second number.

Scope

What this is not

PAAC is a verification primitive for code diffs, not an alignment technique. It does not make an agent's objectives safer, detect deception, or constrain what a capable system does inside an accepted modification. Below is the list a reviewer would otherwise have to find, ordered by how much each limits the safety claim.

Ordered by how much each limits the claim

  • Composition is unguarded. Two confirmed witnesses, zero rejected. This is the binding limitation and everything below it is smaller.
  • The precondition still comes from the agent. A satisfiability gate now rejects unsatisfiable ones, which closes a total verifier bypass. It does not change the fact that an obligation on the caller is supplied by the callee's author.
  • SIL cannot express real agent code. No heap, no pointers, no recursion, no concurrency. This is the standing objection and it is correct. It is also the reason the decision procedure is tractable.
  • Loop bounds are declared, not inferred. Soundness requires the declared bound to cover every reachable input. An under-bounded loop is classified unsafe, which is the safe direction.
  • Self-verification checks tautologies. The shipped stubs assert properties implied by their own guards, so UNSAT follows syntactically. It is not a proof about the verifier.
  • The bounded-loop Z3 step is a certificate, not a proof. It asserts that a literal already constrained below the cap exceeds it. The denial-of-service guarantee is real and comes from the parser and the runtime.
  • Attestation verification is self-referential. The endpoint checks a record against the public key inside that same record, so it proves consistency rather than provenance until an expected key is pinned.
  • Proof-carrying certificates are symmetric. HMAC under a key with a publicly known default, and the proof checker has never been differentially tested against the solver it replaces.
  • Compiler gaps. Division by zero is undetected. A missing return is a warning. Strings encode to unconstrained integers.
  • Unauthenticated by default. With no API key configured the check is skipped and every endpoint is open.
